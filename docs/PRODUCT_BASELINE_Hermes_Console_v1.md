# Hermes Console 产品基线文档 v1.0

> 用途：放入项目目录，作为 **产品方向基线 + UI/UX 约束 + Codex 开发约束**。  
> 目标：让 Codex、开发者、设计师在实现过程中始终围绕同一套边界工作，避免功能扩散、页面失控、风格漂移、术语混乱。  
> 状态：适用于 Hermes Console 第一版（v1）。

---

## 0. 如何使用这份文档

这不是宣传文档，也不是泛泛的 PRD；它是 **项目执行文档**。

使用方式：

1. **每次让 Codex 开始做功能前**，先让它读取本文件。
2. **任何新增功能**，先判断是否在本文档定义的范围内。
3. **任何页面结构修改**，先更新本文档，再改代码。
4. **UI 不确定时**，以本文档的页面职责、组件规则、术语规则为准。
5. **评审时**，以本文档的“验收标准”和“禁止项”作为判断依据。

一句话：

> 代码可以迭代，但产品边界不能每轮 prompt 都被重写。

## 1. 文档目标

本文件解决 5 个问题：

1. Hermes Console 第一版到底是什么，不是什么。
2. 第一版应该做哪些页面、哪些对象、哪些流程。
3. 当前 Figma 成稿背后的产品结构到底如何落到代码层。
4. Codex 在开发时哪些可以改，哪些绝对不能动。
5. 如何防止“功能越做越多、页面越做越乱、风格越做越偏”。

本文件的优先级高于：

- 临时灵感
- 某次对话里的随口需求
- 没有被记录的结构修改
- “顺手加一下”式的页面扩展
- Codex 自主发挥出来的新模块

## 2. 产品定义

### 2.1 一句话定义

**Hermes Console 是一款桌面客户端，用于安装、连接、配置、聊天、管理和运维 Hermes Agent。**

### 2.2 产品角色

Hermes Console 的角色是：

- Hermes 的桌面控制台
- 本地与远程实例的可视化管理壳层
- 面向开发者和 AI 重度用户的生产力工具

### 2.3 它不是什么

Hermes Console **不是**：

- 通用 AI 聊天软件
- 代码 IDE
- 通用 DevOps 平台
- 云主机购买面板
- 大而全的服务器运维后台
- 重写 Hermes 官方全部 Dashboard 的替代品
- 另一个“什么都能放进去”的超级工作台

### 2.4 它是什么

Hermes Console **是**：

- 一个让用户从图形界面完成 Hermes 安装、运行、接入、使用与维护的桌面产品
- 一个把“实例 → 档案 → 会话 / Provider / 集成 / 日志 / 备份”串起来的控制台
- 一个白色、克制、高级、稳定的桌面化 AI 管理工具

## 3. 产品目标

### 3.1 v1 北极星目标

让用户可以在 **本地** 或 **远程 Linux 服务器** 上：

1. 创建 Hermes 实例
2. 选择本机安装或服务器部署
3. 配置 Hermes 官方 Provider 与默认档案
4. 进入会话工作区使用 Hermes
5. 查看日志、管理集成、做备份与恢复

### 3.2 v1 成功标准

以下条件满足，即可视为 v1 成立：

- 用户可从零完成实例创建与部署。
- 用户能明确知道当前连接的是哪个实例、哪个档案、哪个模型。
- 用户能在会话页完成实际工作，而不是只看到展示界面。
- 用户能在日志页定位问题，在备份页完成恢复。
- 用户能在提供商页和集成页完成接入与管理。
- UI 和信息架构在迭代过程中没有被破坏。

### 3.3 v1 不是为了追求的指标

以下不是 v1 的优先目标：

- 功能数量最多
- 页面数量最多
- 支持所有云厂商 API
- 做成团队协作平台
- 把所有高级配置都图形化平铺出来

## 4. 目标用户

### 4.1 主用户 A：独立开发者 / 技术创作者

需求：

- 本地快速跑起 Hermes
- 快速切换档案与模型
- 通过一个桌面工具管理多个实例
- 在遇到错误时快速排查与恢复

### 4.2 主用户 B：在云服务器上跑 Hermes 的 AI 重度用户

需求：

- 通过 SSH 管理远程 Linux 实例
- 快速完成部署、检查、更新与备份
- 不想长期在 CLI 和多个网页间来回切换

### 4.3 次用户 C：有一点技术能力但不想长期用命令行的人

需求：

- 更友好的图形化安装和连接
- 更清晰的错误反馈与恢复建议
- 更低的 Hermes 上手门槛

## 5. 平台与技术边界

### 5.1 客户端形态

Hermes Console v1 为：

- 桌面客户端
- 首发平台：macOS、Windows

### 5.2 本地运行边界

- macOS：支持本地 Hermes 运行
- Windows：本地 Hermes 运行基于 **WSL2**，不是原生 Windows daemon

### 5.3 远程运行边界

- 远程目标仅支持 **SSH 到 Linux 服务器**
- 不接入云厂商创建/管理服务器 API

### 5.4 安装方式边界

v1 底层必须保留：

- Native 安装
- Docker 安装

上线前主流程默认隐藏 Docker 部署入口；用户侧优先表达为“本机安装 / 服务器部署 / 网关服务”，Docker 只出现在技术详情、诊断详情或旧实例管理中。

### 5.5 安全边界

默认安全模型：

- localhost
- SSH 隧道

v1 不以“直接公网暴露管理端口”为默认方案。

### 5.6 真实能力来源

Hermes Console 本质上是管理壳层，不是另造一套 Hermes 内核。

工程上应优先复用：

- Hermes CLI
- Hermes API / 本地服务
- Hermes 原有状态目录
- SSH 通道
- 本机安装 / 服务器部署流程
- 旧实例的技术部署能力

不应该做的事：

- 在客户端里再维护一套与 Hermes 平行的配置真相源
- 在项目里复制一套脱离 Hermes 的“伪状态系统”

## 6. 范围与非范围

### 6.1 v1 必做模块

v1 只做以下 11 个模块：

1. 首次启动 / 欢迎页
2. Dashboard（实例总览）
3. 创建实例向导
4. 实例概览页
5. 会话页
6. 档案页
7. 提供商页
8. 集成页
9. 日志与诊断页
10. 备份与恢复页
11. 设置页

### 6.2 v1 不做

以下能力不得在 v1 私自扩展进入：

- 云服务器购买 / 开机 / 续费 / 厂商 API 接入
- 多人团队权限系统 / RBAC
- 通用插件市场
- IDE / 代码编辑器
- 新的一级导航页
- 大型监控中心 / 分析中心 / 资源中心
- 对 Hermes 官方高级面板的完整重写
- 任意“想到一个就加一个”的平铺功能区

### 6.3 变更准入规则

任何新需求，必须先回答 3 个问题：

1. 它是否属于上述 11 个模块之一？
2. 它能否挂载到现有页面，而不是新开页面？
3. 它是否会破坏当前信息架构或组件系统？

只要有任一答案为“会”，该需求默认进入 **vNext 待评估**，不得直接开发。

## 7. 核心对象模型

Hermes Console v1 只围绕以下 6 个对象展开：

### 7.1 Instance（实例）

定义：一套 Hermes 运行环境。

字段建议：

- id
- 名称
- 本地 / 远程
- 平台
- 安装方式（Native / Docker）
- 版本
- 当前状态
- 默认档案
- 最近活动时间
- 连接健康度

### 7.2 Profile（档案）

定义：实例下的隔离 Hermes 运行环境 / official profile。

作用：

- 隔离模型与 Provider 配置
- 隔离会话
- 隔离某些集成与运行上下文

字段建议：

- id
- 名称
- 是否默认
- provider / model 摘要
- 会话数量
- gateway 状态
- 最近使用时间

### 7.3 Provider（提供商）

定义：官方 model/provider 配置对象。

分组：

- OAuth 型
- API 密钥型
- 自定义 Endpoint 型
- 自托管型

### 7.4 Integration（集成）

定义：Hermes 原生消息平台接入。该页只管理聊天/消息平台凭据与 profile 级配置，不承载程序化访问、编辑器协议、自动化回调或扩展入口。

分组：

- Telegram
- 微信 / Weixin
- QQ
- 飞书 / Lark

### 7.5 Session（会话）

定义：用户与 Hermes 的单次对话上下文。

### 7.6 Backup（备份）

定义：实例或档案在某一时刻的可恢复快照。

## 9. 产品设计原则

### 9.1 一级对象永远是“实例”

用户进入产品后，最高层永远是实例，不允许被新的主对象替代。

### 9.2 档案是二级核心对象

档案是实例下的隔离 Hermes profile，不是普通标签页，不是轻量筛选条件。

### 9.3 会话是主要工作界面，但不是消费级聊天软件

聊天页必须是专业工作区，而不是社交聊天 App。

### 9.4 高级配置默认隐藏

高级配置只能进入：

- 抽屉
- 模态
- 二级设置区
- 高级面板入口

不得平铺到主工作区。

### 9.5 不新增一级导航

新功能只能挂载到：

- 现有页面
- 现有抽屉
- 现有模态
- 现有设置分组

### 9.6 日志重要，但不得抢主视图

尤其是在部署流程中，日志必须作为辅助反馈，而不是页面视觉主角。

### 9.7 产品是桌面工具，不是营销站

所有页面都应体现：

- 可扫描
- 可操作
- 可恢复
- 有秩序
- 有边界

## 10. 视觉与品牌基线

### 10.1 视觉方向

- 白色主体
- Light-first
- 暖白背景
- 纯白卡片
- 轻阴影
- 浅边框

### 10.2 关键词

- 极简
- 高级
- 安静
- 可信赖
- 桌面化
- 专业

### 10.3 禁止项

禁止出现：

- 暗色主界面
- 赛博朋克
- 大面积渐变
- 过度玻璃拟态
- 游戏化状态色
- 超高饱和配色
- 杂乱仪表盘风

### 10.4 颜色使用规则

- 蓝色：主动作、当前态、关键强调
- 绿色：成功、已连接、活跃
- 橙色：警告
- 红色：危险、删除、错误
- 所有状态色均为低饱和

### 10.5 留白与密度原则

Hermes Console 不是展示页，不应为了“高级感”而过度空白。

要求：

- 信息密度要高于营销站
- 但低于臃肿运维后台
- 留白必须服务于层级，而不是制造空洞

## 11. 信息架构

v1 只允许以下一级导航：

1. 概览
2. 会话
3. 档案
4. 提供商
5. 集成
6. 日志
7. 备份
8. 设置

### 11.1 固定左侧结构

左侧区域固定为三层：

1. 品牌区
2. 当前实例区域
3. 工作区导航

### 11.2 固定顶部结构

顶部工具栏统一包含：

- 搜索 / 命令入口
- 安全连接状态
- 当前档案
- 当前模型或环境摘要
- 轻量快捷动作

### 11.3 主内容区规则

- 每页只能有一个主内容区
- 最多 3 层信息层级
- 不允许随机漂浮功能区
- 不允许把所有功能堆在首页

## 12. 页面规格说明

### 12.1 首次启动 / 欢迎页

#### 页面目标

帮助用户理解产品作用，并快速进入实例创建流程。

#### 必须包含

- 产品欢迎语
- 添加本地实例
- 添加远程实例
- 简短安全说明（默认 localhost + SSH 隧道）
- Native / Docker 的简短说明

#### 不允许

- 展示过多设置项
- 变成产品介绍长页面
- 用很多营销文案代替操作

---

### 12.2 Dashboard（实例总览）

#### 页面目标

展示所有实例与总览状态，帮助用户快速进入某个实例工作区。

#### 必须包含

- 页面标题
- 新建实例入口
- 实例卡片列表
- 状态标签
- 最近更新时间

#### 实例卡片最少字段

- 实例名称
- 本地 / 远程
- 平台
- 安装方式
- 版本
- 运行状态
- 默认档案
- 最近活动时间

#### 允许的辅助区域

- 轻量健康摘要
- 轻量最近活动摘要

#### 不允许

- 首页塞入大型日志区
- 首页承载完整监控页职责
- 首页出现多个与实例无关的业务模块

---

### 12.3 创建实例向导

#### 页面目标

让用户以最清晰、最可信赖的方式完成实例创建与部署。

#### 流程固定为 5 步

1. 目标
2. 环境与连接检查
3. 安装方式
4. 提供商与档案
5. 最终确认与部署

#### Step 1：目标

必须支持：

- 本地实例
- 远程实例

说明应覆盖：

- macOS
- Windows WSL2
- 远程 Linux via SSH

#### Step 2：环境与连接检查

必须支持以下状态：

- 通过
- 警告
- 失败
- 可重试
- 修复建议

本地检查项建议：

- 操作系统可用性
- 运行服务
- Hermes 工作目录可写
- 网络访问
- 端口可用性

远程检查项建议：

- SSH 连通性
- 用户权限
- 远程可写目录
- 运行服务
- 磁盘空间
- 端口冲突

#### Step 3：部署方式

上线前主流程仅展示：

- 本机安装
- 服务器部署

必须解释：

- 隔离程度
- 可迁移性
- 权限边界
- 适用场景

#### Step 4：提供商与档案

必须允许配置：

- Hermes 官方 Provider / model 配置
- Provider
- 模型
- 默认档案名称
- 默认档案映射为 Hermes profile
- 按 provider 动态呈现字段

说明应明确：

- Provider 相关字段来自官方配置对象
- 默认档案与 Hermes profile 一一对应
- 新手路径只保留“选供应商 → 登录或粘贴 Key → 保存 → 测试”
- 不把“自动选择”作为新手可选项

#### Step 5：最终确认与部署

必须显示：

- 目标类型
- 安装方式
- Provider
- 模型
- 默认档案
- 消息接入在集成页配置
- 本地路径或远程目标摘要
- 安全方式
- 开始部署按钮

#### 部署中（Running）

必须显示：

- 当前步骤
- 总进度
- 当前执行任务
- 实时日志
- 取消 / 重试 / 异常反馈

#### 成功（Success）

必须显示：

- 创建成功
- 当前实例名
- 访问方式或地址摘要
- 安全连接方式
- 下一步动作：
  - 进入工作区
  - 打开会话
  - 打开高级面板

---

### 12.4 实例概览页

#### 页面目标

作为单实例的总控页，承载当前实例的整体状态与快捷操作。

#### 必须包含

- 实例名称
- 本地 / 远程
- 安装方式
- 版本
- 健康状态
- 当前档案
- 当前模型
- SSH 状态 / 连接状态
- 快捷操作区
- 健康卡片
- 活动时间线

#### 快捷操作允许包含

- 启动
- 停止
- 重启
- 打开会话
- 创建备份
- 更新
- 打开高级面板

#### 规则

- 必须有一个主动作
- 其余动作降为次动作
- 不允许所有按钮同权重

---

### 12.5 会话页

#### 页面目标

作为 Hermes 的核心工作界面。

#### 布局固定为三栏

##### 左栏

- 新建会话
- 搜索
- 会话列表

##### 中栏

- 消息流
- 工具调用过程
- 错误输出 / 日志回显
- 输入框
- 发送动作

##### 右栏

- 当前档案
- 当前模型 / 提供商
- 工具状态
- 会话元数据
- 上下文信息

#### 必须区分的内容类型

- 用户消息
- Hermes 回复
- 工具调用信息
- 错误输出
- 最终结论

#### 不允许

- 采用消费级聊天大气泡风格
- 加入社交元素
- 把右栏做成杂项堆叠区

---

### 12.6 档案页

#### 页面目标

管理实例下的隔离 Hermes profile。

#### 必须支持

- 新建档案
- 克隆档案
- 重命名
- 删除
- 导出
- 导入
- 设为默认

#### 每张档案卡片至少包含

- 档案名称
- provider / model 摘要
- 会话数量
- gateway 状态
- 最近使用时间
- 默认状态

#### 页面必须强调

“档案是相互隔离的 Hermes profile”。

---

### 12.7 提供商页

#### 页面目标

管理 Hermes 官方 model/provider 配置。

#### 页面结构

采用“目录 + 抽屉详情”模式。

#### 排序建议

- 已配置 / 当前 provider
- 新手常用 provider
- 其他官方 provider

#### 卡片字段

- 名称
- 状态
- 配置方式
- 推荐模型
- 管理入口

#### 列表页规则

- 列表页负责扫描与定位
- 抽屉负责“登录或粘贴 Key → 保存 → 测试”
- 字段按 provider 动态呈现，不做统一大表单
- 不展示内部自动选择 provider

#### 详情抽屉必须允许配置

- 认证方式
- 默认模型
- 必填凭据 / Endpoint
- 测试连接

#### 必须支持状态

- 已连接
- 未配置
- 连接失败

---

### 12.8 集成页

#### 页面目标

管理 Hermes 原生消息平台。

#### 页面结构

采用“消息平台目录 + 抽屉详情 + profile 选择器”模式。

#### 平台建议

- Telegram
- 微信 / Weixin
- QQ
- 飞书 / Lark

#### 卡片字段

- 集成名称
- 接入类型
- 当前状态
- 健康摘要
- 管理入口

#### 详情抽屉必须允许配置

- 必填字段配置
- 敏感字段空值保持原值
- 保存配置
- 状态说明

#### 必须支持状态

- 已启用
- 未启用
- 异常
- 活跃
- 未同步

#### 不作为核心对象

- Skills
- Plugins
- 程序化访问
- 编辑器协议
- 自动化回调
- 智能家居入口

### 12.9 日志与诊断页

#### 页面目标

用于排查问题与辅助恢复。

#### 必须包含标签

- Agent 日志
- Gateway 日志
- 错误日志
- 诊断

#### 必须支持

- 搜索
- 过滤
- 时间戳

- 复制错误摘要

#### 页面角色

- 主体为日志区
- 诊断区为辅助
- 不做黑底终端首页

### 12.10 备份与恢复页

#### 页面目标

管理快照、备份、恢复与维护动作。

#### 必须支持

- 创建备份
- 快照
- 导入
- 恢复

#### 每条备份至少显示

- 日期
- 大小
- 范围
- 来源实例 / 档案

#### 必须区分

- 常规备份动作
- 恢复动作
- 危险维护动作

#### 危险动作必须单独分区

- 恢复
- 清理
- 卸载

### 12.11 设置页

#### 页面目标

仅承载应用偏好、Hermes 配置摘要与维护入口。

#### 只允许包含

- 显示语言
- 主题
- Hermes 配置摘要
- 维护入口
- 打开高级面板入口

#### 不允许

- 把 Hermes 全部高级配置平铺到设置页
- 设置页承担实例级或部署级管理职责
- 侧边栏底部再放第二个语言入口
- SSH 默认项、日志偏好、安装偏好这类旧入口

## 13. 组件系统规范

### 13.1 组件白名单

第一版开发只允许复用以下组件体系：

- Sidebar
- Topbar
- Search / Command Bar
- Card
- Table
- List
- Tabs
- Badge
- Button
- Input
- Select
- Toggle
- Stepper
- Drawer
- Modal
- Empty State
- Log Panel
- Timeline
- Split View

### 13.2 禁止项

禁止以下行为：

- 页面内临时拼装新的布局体系
- 为单一功能创建看似独立的新页面壳层
- 随手新增漂浮模块
- 创建“这页专用、别页不用”的样式系统
- 用新的按钮层级破坏全局规则

### 13.3 抽屉统一结构

每个抽屉必须遵守：

1. 标题区
2. 说明区
3. 主内容区
4. 状态区（可选）
5. 风险提示区（可选）
6. 底部按钮区

### 13.4 模态统一结构

每个模态必须遵守：

1. 标题
2. 简短说明
3. 核心确认区
4. 风险提示
5. 操作按钮

### 13.5 按钮规则

单个页面内只允许：

- 1 个主按钮
- 若干次按钮
- 必要时 1 个危险按钮

禁止页面内出现多个同权重主按钮。

## 14. 状态设计规范

v1 必须覆盖以下状态：

- 空状态
- 加载态
- 骨架屏
- 成功态
- 错误态
- 警告态
- 离线态
- 运行中
- 可重试失败态

### 14.1 空状态规则

空状态必须说明：

- 为什么为空
- 当前页有什么作用
- 下一步主动作是什么

### 14.2 错误态规则

错误态必须说明：

- 问题是什么
- 影响范围是什么
- 推荐恢复动作是什么
- 是否可重试

### 14.3 运行中规则

运行中状态必须展示：

- 正在做什么
- 做到哪一步
- 下一步是什么
- 当前是否可取消或重试

## 15. 文案规则

### 15.1 语言策略

v1 以 **简体中文** 为主。

### 15.2 保留英文的情况

仅允许保留不可避免的技术名词：

- OAuth
- API
- Endpoint
- SSH
- Docker（仅技术详情、诊断详情或旧实例管理）
- Webhook
- Socket

### 15.3 不允许

- 中英并列标题
- 一半中文一半英文的按钮
- 不同页面使用不同术语翻译
- 把设置页做成中英混搭试验场

### 15.4 文案气质

文案应当：

- 短
- 清楚
- 专业
- 克制
- 不营销化

---

## 16. Codex 开发约束协议

以下规则应视为 **Codex 必须遵守的开发协议**。

### 16.1 结构冻结

Codex 不允许：

- 新增一级导航
- 重新定义页面层级
- 新建未批准页面
- 在主页面中随意插入独立功能区

### 16.2 功能挂载原则

任何新增功能必须明确挂载到下列之一：

- 概览
- 会话
- 档案
- 提供商
- 集成
- 日志
- 备份
- 设置
- 已有抽屉
- 已有模态

禁止无锚点新增模块。

### 16.3 组件复用原则

Codex 不允许创建“看起来差不多、实际上不同”的重复组件。

### 16.4 文案一致性原则

所有可见文案必须优先使用本文档术语表。

### 16.5 风格不可漂移

Codex 不允许：

- 把主界面改成暗色主主题
- 引入高饱和大面积色块
- 引入过重的终端黑块作为页面主角
- 把控制台改造成营销风产品页

### 16.6 高级配置不可下放

高级配置只能进入：

- 抽屉
- 模态
- 二级区域
- 高级面板入口

不得平铺到核心工作界面。

### 16.7 日志不可抢主视图

尤其在部署流程中，日志必须是辅助反馈，不得压过流程主内容。

### 16.8 页面主 CTA 规则

任何页面只能有一个最明显的主 CTA。

### 16.9 先读文档再动代码

每次开始新功能前，Codex 必须先读取：

- 本产品基线文档
- 当前页面对应的页面规格
- 当前组件规范

## 17. 数据与状态建议（工程层）

> 这是产品文档中的工程约束建议，不是技术实现细节说明书。

### 17.1 状态真相源

优先原则：

- Hermes 自身目录与运行状态是真相源
- 客户端保存的是 UI 索引和连接元数据，不应复制一套“平行真实状态”

### 17.2 建议区分的状态层

#### A. 全局应用状态

- 当前实例
- 当前档案
- 语言
- 主题
- Hermes 配置摘要入口

#### B. 实例状态

- 在线 / 离线
- 部署中
- 更新中
- 健康异常
- 最近活动时间

#### C. 页面局部状态

- 列表加载
- 抽屉打开
- 模态确认
- 日志流中
- 表单校验中

### 17.3 状态呈现规则

- 不要在一个页面里同时展示过多层级状态
- 状态标签必须可快速扫描
- 错误信息必须能被复制或二次展开查看

## 19. Definition of Done（完成定义）

一个页面或功能只有同时满足以下条件，才算完成：

1. 满足本文档中对应页面的职责定义。
2. 没有新增未批准的页面结构。
3. 没有新增新的一级导航或新的主布局模式。
4. 复用了现有组件体系。
5. 中文术语统一。
6. 主按钮层级清楚。
7. 覆盖空状态、错误态、加载态。
8. 在白色主题下视觉仍保持克制与秩序。
9. 不依赖“以后再整理”的临时 UI。
10. 对应交互可以被明确验收。

## 20. 验收清单

每次提交前必须自检以下 12 项：

1. 有没有新增页面？
2. 有没有新增一级导航？
3. 有没有改变页面层级？
4. 有没有新增漂浮模块？
5. 有没有把高级配置平铺到主界面？
6. 有没有出现中英混用？
7. 有没有新增不复用的临时组件？
8. 有没有多个主 CTA 同时抢焦点？
9. 有没有日志区域抢走主视图？
10. 有没有明显破坏白色高级感？
11. 有没有功能挂载不清楚的地方？
12. 有没有“这版先这样，以后再收”的 UI 债？

只要任意一项为“有”，默认不应合并到主分支。

## 21. 变更管理规则

### 21.1 什么改动必须先改文档

以下改动必须先更新本文档，再进入开发：

- 新增页面
- 修改一级导航
- 修改对象模型
- 新增核心对象
- 修改页面职责
- 新增全局组件规则
- 修改语言策略
- 修改视觉基线

### 21.2 什么改动可以不先改文档

以下可以在不更新本文档的情况下实施：

- 微调间距
- 修正错别字
- 调整某个按钮文案但不改变含义
- 修复明显视觉 Bug
- 完善状态反馈但不改变页面职责

## 24. 当前版本结论

Hermes Console v1 当前应被理解为：

- 一个边界明确的桌面控制台
- 一个围绕“实例”与“档案”构建的 AI 管理工具
- 一个以白色、中文、桌面化、专业感为基线的产品
- 一个必须通过文档驱动来防止开发偏移的项目

这份文档的核心价值不是“把产品说得更完整”，而是：

> **让后续每一次 Codex 开发都围绕同一套边界工作，不再因为 prompt 漂移而把产品做乱。**

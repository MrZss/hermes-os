# AI 提供商真实对接设计

日期：2026-05-04

## 1. 背景

当前 Hermes Console 的远程节点 UI / UX 已经完成节点化收口，Providers 页面也已经具备基础卡片、抽屉、OAuth 按钮和测试入口。但现阶段更偏向“界面已成型”，还没有把“配置真实保存、状态真实回读、测试真实落地”这一层完全收口成稳定闭环。

产品当前定位很明确：

- 本地实例 = 创作工作区
- 远程实例 = 部署与接入节点
- AI 提供商配置必须足够傻瓜式，让用户尽快跑通

因此下一阶段不再重做交互框架，而是把 Providers 页从“好看可点”推进到“真实可用”。

---

## 2. 本阶段目标

本阶段只解决以下四件事：

1. **Provider 配置真实保存**
2. **OAuth / API Key 真实接入**
3. **连通性测试真实执行并回写**
4. **默认模型真实保存并回填**

本阶段的目标不是重做页面，而是在现有页面形态上，把所有关键状态改成以真实实例状态为准。

---

## 3. 范围边界

### 3.1 本阶段包含

- Providers 页真实读取当前实例官方状态
- 保存 Provider 配置后立即回读官方状态
- OAuth 登录动作真实触发并刷新状态
- API Key 模式真实保存
- 测试按钮真实执行并展示结果
- 默认模型保存后刷新展示
- 已配置 / 已验证 Provider 排序前置
- 本地实例与远程节点共用同一套真实对接逻辑

### 3.2 本阶段明确不做

- 会话真实调用 Provider
- 聊天链路联动 Provider 真实推理
- 档案级 Provider 隔离重构
- 新的 Provider Wizard 流程重做
- 凭据加密体系重构
- 多 Provider 路由/回退策略重构
- 提供商目录体系大改

这样能保证阶段目标聚焦，不把“配置对接”与“会话推理”两个不同系统混在一起。

---

## 4. 方案对比

### 方案 A：实例级直写直读（推荐）

Providers 页所有关键动作都直接走桌面桥：

- 保存：`updateInstanceProviderConfig(...)`
- OAuth：`authenticateInstanceProvider(...)`
- 测试：`testInstanceProvider(...)`
- 回读：`getInstanceOfficialState(...)` + `listInstanceProviderTests(...)`

页面只保留少量临时表单状态，最终展示结果一律以实例真实状态为准。

**优点**
- 与 Hermes Console 桌面客户端定位一致
- 不会出现“页面显示已保存，实例真实没生效”的割裂
- 本地与远程节点可共享一致逻辑
- 容易和后续消息平台、节点状态联动

**缺点**
- 依赖桌面桥返回质量
- 页面状态管理会比纯前端假数据更严格

### 方案 B：前端先保存草稿，再异步同步

先在前端维护一层 provider draft，保存时再后台同步到实例。

**优点**
- 交互更顺滑
- 表单可以支持更复杂的半成品编辑

**缺点**
- 容易造成“草稿状态”和“真实状态”分裂
- 不符合“傻瓜式配置、尽快跑通”的产品目标

### 方案 C：重做为完整 Provider 向导

将 Providers 改造成单独的引导式向导。

**优点**
- 对新手最友好
- 流程最明确

**缺点**
- 改动过大
- 会打断当前已经收口好的远程节点工作流
- 不适合当前阶段“先把真实对接做完”这个目标

### 结论

本阶段采用 **方案 A：实例级直写直读**。

---

## 5. 设计原则

### 5.1 真实状态优先

Providers 页看到的最终状态必须来自实例真实状态，而不是前端猜测。

### 5.2 傻瓜式优先

用户只需要理解：

1. 选供应商
2. 登录或填 Key
3. 保存
4. 测试

不需要理解 Hermes 内部配置文件、credential pool 或更底层机制。

### 5.3 节点化一致性

远程节点下的 Providers 页必须延续节点化逻辑：

- 状态清晰
- 下一步明确
- 错误提示人话化
- 不展示和会话型工作区相关的噪音

---

## 6. 页面行为设计

### 6.1 Providers 页总览

保留当前卡片式结构，但卡片状态统一改为真实数据驱动。

每张 Provider 卡片至少展示：

- 供应商名称
- 推荐/默认模型
- 当前连接状态：未配置 / 已连接 / 验证失败 / 已验证
- 认证方式摘要：OAuth / API Key / Endpoint
- 最近测试结果（如有）
- 最近测试时间（如有）

页面顶部保持新手路径提示：

> 选供应商 → 登录或粘贴 Key → 保存 → 测试

### 6.2 排序规则

Provider 卡片按以下优先级排序：

1. 当前实例的默认 Provider
2. 已连接且已验证
3. 已连接但未验证
4. 已配置但测试失败
5. 未配置
6. 按新手优先顺序补齐：
   - OpenAI Codex
   - Anthropic
   - DeepSeek
   - OpenRouter
   - Gemini
   - DashScope
   - Custom Endpoint

### 6.3 Drawer 行为

Drawer 只保留必要内容：

- 供应商名称
- 认证方式
- 默认模型
- Base URL（仅 custom / endpoint 类）
- API Key（仅对应方式）
- OAuth 说明和按钮（仅 OAuth 类）

明确隐藏：

- 高级配置块
- 自动选择
- 底层实现细节
- 无关英文技术摘要

---

## 7. 动作链路设计

### 7.1 保存配置

动作入口：
- Drawer 中“保存并设为当前供应商”

调用：
- `updateInstanceProviderConfig(instanceId, payload)`

保存成功后：
1. 保持当前 Drawer 上下文
2. 回读 `getInstanceOfficialState(instanceId)`
3. 重新读取 `listInstanceProviderTests(instanceId)`
4. 刷新卡片状态、默认模型、当前 provider 显示
5. 给出明确成功反馈

失败时：
- 显示人话错误
- 不暴露长技术栈
- 继续保留表单当前值，避免用户重填

### 7.2 OAuth 登录

动作入口：
- Drawer 中 OAuth 登录按钮

调用：
- `authenticateInstanceProvider(instanceId, payload)`

成功后：
1. 回读官方状态
2. 更新 provider 卡片状态
3. 如果当前 provider 已连接，将其前置
4. 显示“已完成登录，建议立即测试”的后续提示

失败时：
- 统一显示“OAuth 登录失败”及人话原因

### 7.3 API Key 保存

动作入口：
- Drawer 中保存按钮

校验：
- 对 API Key 模式必须有真实凭据
- custom endpoint 场景必须校验模型和 base_url

成功后：
- 与保存配置链路相同：保存 → 回读 → 刷新 → 反馈

### 7.4 测试 Provider

动作入口：
- Provider 卡片按钮或 Drawer 中测试按钮

调用：
- `testInstanceProvider(instanceId, payload)`

测试结果映射：
- `verified` → 已验证
- `failed` → 验证失败
- `configured` → 已配置（未验证）

测试成功后：
- 立刻刷新最近测试时间与状态 badge
- 当前 provider 若通过测试，优先展示为已验证

---

## 8. 数据优先级

统一规定页面状态来源优先级：

1. **官方状态回读**
2. **Provider Test 结果**
3. **当前临时表单状态**

解释：
- 卡片最终显示必须以官方状态为准
- 测试 badge 以测试结果为准
- 表单只负责用户正在输入时的临时体验

这样可以避免页面状态与真实实例状态分裂。

---

## 9. 远程节点适配要求

远程节点下的 Providers 页要满足：

- 状态刷新不依赖手动重进页面
- 保存 / OAuth / 测试完成后自动更新当前页状态
- 与远程节点的概况 / 部署 / 诊断叙事一致
- 错误文案继续保持人话化

不允许出现：
- 浏览器预览风格的假成功状态
- OAuth 成功但卡片没刷新
- 测试成功但列表排序不变
- 顶部继续显示会话型噪音信息

---

## 10. 验收标准

### 10.1 本地实例

- 选择 API Key Provider，可真实保存并回读
- 选择 OAuth Provider，可真实发起认证并回读状态
- 默认模型保存后刷新可见
- 测试动作真实执行，结果正确显示
- 已连接 / 已验证 Provider 自动前置

### 10.2 远程节点

- 在远程节点 Providers 页重复上述链路
- 状态刷新无需手动重进页面
- 错误提示为人话，不暴露技术噪音

### 10.3 桌面端验收

必须在 Electron 客户端内完成：

- 打开 Provider 卡片
- 保存配置
- 触发 OAuth 或 API Key 保存
- 执行测试
- 观察卡片、排序、状态、反馈是否即时更新

---

## 11. 风险与后续

### 本阶段风险

- 桌面桥返回状态与 UI 假设不一致时，可能暴露旧逻辑分叉
- 不同 Provider 的认证方式差异较大，需避免在页面里硬编码过多特例

### 后续阶段自然衔接

本阶段完成后，下一阶段最自然的继续方向是：

1. **消息平台真实对接**
2. **远程节点运维动作和 Provider 状态联动**
3. **会话真实调用 Provider**

这样顺序是从“配置可用”走向“能力可用”，而不是一步把所有链路混在一起。

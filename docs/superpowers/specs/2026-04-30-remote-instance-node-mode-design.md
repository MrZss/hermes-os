# 远程实例节点化设计

## 背景
当前 HermesOS 将本地实例与远程实例都按“工作区/会话型”产品建模，但真实运行边界并不一致：

- 本地实例可以稳定持有进程、文件、状态与会话上下文，适合持续会话与工作区交互。
- 远程实例当前依赖 SSH + 远程 Docker / Hermes Gateway，天然更接近“部署节点”而不是“创作工作区”。
- 用户已明确接受：远程实例可以不做完整会话逻辑。

因此需要将远程实例从“会话型工作区”重构为“部署与接入节点”，降低错误预期，并让 IA（信息架构）、导航与交互更符合真实能力边界。

## 目标
将远程实例重新定义为“部署与接入节点”，默认不提供持续会话/工作区型入口，而是聚焦：

- 环境检查
- 部署管理
- AI 提供商配置
- 消息平台接入
- 日志与诊断
- 启停/重建/清理等运维动作

## 非目标
本次不做以下内容：

- 不为远程实例实现稳定长连接会话
- 不保证远程实例拥有与本地实例一致的 Chat / Workspace 体验
- 不重构本地实例的信息架构
- 不设计新的安全存储方案（沿用当前远程连接信息存储模型）

## 产品定义

### 本地实例
定位：**创作工作区**

保留能力：
- 会话
- 工作区上下文
- 档案
- AI 提供商
- 消息平台
- 日志
- 备份

### 远程实例
定位：**部署与接入节点**

核心能力：
- SSH / Docker / Gateway 状态检查
- 远程目录与端口检查
- 启动 / 停止 / 重启 / 重建
- AI 提供商配置
- 消息平台接入
- 日志
- 运行诊断

默认不强调能力：
- 持续会话
- 工作区型上下文浏览
- 档案驱动型多会话操作

## 信息架构

### 本地实例导航（保留现状）
- 概况
- 会话
- 档案
- 提供商
- 集成
- 日志
- 备份

### 远程实例导航（重构后）
- 概况
- 环境检查
- 部署管理
- AI 提供商
- 消息平台
- 日志
- 诊断

## 页面设计

### 1. 远程概况
展示：
- SSH 目标
- 运行状态
- Docker 状态
- Gateway 状态
- 当前工作目录
- 映射端口
- 最近错误

主操作：
- 读取环境
- 启动
- 停止
- 重建
- 卸载

### 2. 环境检查
展示：
- SSH 认证是否通过
- 远程目录状态
- Docker daemon 状态
- 端口可用状态
- Hermes CLI 检测结果（如有）
- 建议修复项

要求：
- 以结果卡片为主，不展示过多底层原始输出
- 原始错误折叠展示

### 3. 部署管理
展示：
- 容器名称
- 镜像名称
- 对外端口
- 内部端口
- 工作目录
- 创建时间
- 最后一次部署结果

操作：
- 重新部署
- 重建容器
- 清理实例目录
- 重启 Gateway

### 4. AI 提供商
保留现有简化配置逻辑。

远程节点中的提供商页只承担“节点侧模型配置”职责，不再与远程会话耦合。

### 5. 消息平台
保留 Telegram / 微信 / QQ / 飞书等原生接入配置。

职责是“让远程节点具备消息入口”，不再强调“把远程节点当聊天工作区”。

### 6. 日志
展示：
- Gateway 日志
- 容器日志
- 错误日志

支持：
- 刷新
- 复制
- 关键错误高亮

### 7. 诊断
展示节点健康摘要：
- 容器状态
- 端口映射
- Health 检查
- Docker 状态
- 最近日志诊断结论

目标是给用户一个“为什么远程节点不可用”的集中答案页。

## 路由策略

### 本地实例
维持现有：
- `/instance/:id`
- `/instance/:id/chat`
- `/instance/:id/profiles`
- `/instance/:id/providers`
- `/instance/:id/integrations`
- `/instance/:id/logs`
- `/instance/:id/backups`

### 远程实例
调整为：
- `/instance/:id`
- `/instance/:id/environment`
- `/instance/:id/deployment`
- `/instance/:id/providers`
- `/instance/:id/integrations`
- `/instance/:id/logs`
- `/instance/:id/diagnostics`

## 兼容与跳转策略
为避免旧链接失效，远程实例访问旧入口时采用软跳转：

- `/chat` → 跳转到 `/deployment` 或 `/environment`
- `/profiles` → 跳转到 `/providers` 或 `/diagnostics`
- `/backups` → 先隐藏，不在远程导航展示；若访问旧链接则跳回概况

并显示提示：

> 远程实例当前定位为部署节点，持续会话与工作区能力仅在本地实例开放。

## 交互原则
- 远程页面文案强调“节点 / 部署 / 接入 / 诊断”，避免使用“会话工作区”措辞
- 优先给出可执行动作，而不是暴露底层实现细节
- 所有后台操作必须有 loading / 当前阶段提示
- 错误优先展示归因与建议，其次才展示原始错误

## 技术设计

### 导航层
在 `RootLayout` 基于实例类型动态生成导航：
- `local` 使用本地工作区导航
- `remote` 使用节点导航

### 路由层
保留现有实例主路由，但新增远程专属子页面组件：
- `Environment`
- `Deployment`
- `Diagnostics`

旧页面中的 `Chat` / `Profiles` / `Backups` 在远程场景下做重定向。

### 能力边界
远程实例仍可保留底层 workspace/profile 代码，但 UI 层不再将其作为一等主流程。这样可以：
- 降低本次重构成本
- 避免一次性删除大量已有逻辑
- 保留后续做“远程短任务式对话”的可能性

## 错误处理
### 远程页面的错误呈现分级
1. **摘要层**：一句话归因
2. **建议层**：告诉用户下一步该做什么
3. **原始错误层**：折叠显示 stdout/stderr/detail

### 典型错误分类
- SSH 不可达
- SSH 认证失败
- Docker 不可用
- 端口冲突
- Gateway 未启动
- Health 检查失败
- 远程目录不可写

## 测试策略
### UI 验收
- 本地实例仍展示会话/档案/备份导航
- 远程实例只展示节点型导航
- 远程访问旧会话页时正确跳转并提示
- 远程部署管理页能显示容器/端口/目录信息
- 远程诊断页能显示错误归因

### 回归测试
- 不影响本地实例现有工作区逻辑
- 不影响提供商/消息平台既有配置流程
- 不影响远程实例现有创建、启动、停止、读取环境能力

## 分阶段实施建议
### Phase 1
- 导航动态分流
- 新增远程页面骨架
- 旧页面远程场景重定向

### Phase 2
- 将远程概况中的部署信息拆到部署管理页
- 将远程诊断从概况中独立出来

### Phase 3
- 统一远程错误提示与 loading
- 做远程节点专属 polish

## 风险
- 现有页面对“远程=工作区”的假设较多，重定向逻辑要覆盖干净
- 若部分远程页面仍隐式依赖 workspace/profile 数据，需在 UI 层明确降级而不是直接报错
- 远程 Gateway health 当前仍存在目标环境侧不稳定现象，诊断页需要正确表达“部署成功但服务未完全健康”的状态

## 结论
推荐将 HermesOS 的实例模型明确拆分为：

- **本地实例 = 创作工作区**
- **远程实例 = 部署与接入节点**

这样既符合真实运行边界，也能显著降低用户对远程长连接会话的错误预期，并为后续远程节点运维体验优化建立清晰结构。
